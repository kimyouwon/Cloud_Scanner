위험도: 10/10
설명: API Server 비인증 접근 차단이 허용될 경우, 익명 요청이 활성화되며 비인가자가 서버에 접근하여 Kubernetes 시스템 환경에 영향을 줄 수 있다.

kubectl get pods -n kube-system -o json | jq '.items[] | select(.metadata.name | contains("kube-apiserver")) | .spec.containers[].args'
해결 방법:
명시적으로 --anonymous-auth=false 설정 및 --service-account-lookup=true 추가

CHK-M-API-005: SSL/TLS 활성화

위험도: 9/10
설명: SSL/TLS 통신 적용을 통해 네트워크 스니핑과 같은 공격으로 주요 정보가 노출되지 않도록 안전한 통신을 해야 하며, API server에 접근하는 대상에 대해 검증할 수 있도록 설정해야 한다. 또한 SSL/TLS 통신 적용 시에는 주기적으로 인증서를 변경하고 안전한 버전의 암호화 방식을 사용하는 방법을 통해 위험을 최소화할 수 있는 정책 설정이 필요하다.
원인: 다음 TLS 관련 플래그가 누락되었거나 값이 비어있음: --kubelet-certificate-authority, --tls-cipher-suites
권장 설정:
API server SSL/TLS가 적용된 경우
- --secure-port 설정
- --kubelet-certificate-authority
- --kubelet-client-certificate
- --kubelet-client-key
- --tls-cert-file
- --tls-private-key-file
- --client-ca-file
- --tls-cipher-suites
확인 명령어:
kubectl get pods -n kube-system -o json | jq '.items[] | select(.metadata.name | contains("kube-apiserver")) | .spec.containers[].args' | grep -E 'secure-port|tls-cert|tls-private-key|client-ca'
해결 방법:
kube-apiserver 매니페스트에 TLS 관련 플래그(예: --tls-cert-file, --tls-private-key-file, --client-ca-file, --kubelet-client-certificate/key 등)를 명시적으로 설정하고 --secure-port가 0이 아닌 안전한 포트로 설정되어 있는지 확인하세요. 또한 --tls-cipher-suites 에 강력한 TLS1.2/1.3 기반 암호화 스위트만 허용하세요.

CHK-M-PSA-001: 컨테이너 권한 제어

위험도: 9/10
설명: PodSecurityAdmission(이하 PSA)는 클러스터 및 네임스페이스 수준의 리소스로, 파드에 대해 서로 다른 격리 수준을 정의한다. PodSecurityStandard(이하 PSS)를 적용하기 위해 내장된 PSA Controller를 통해 수행된다. PSS 수준에 맞지 않은 Pod를 생성할 경우 설정된 PSS 수준에 따라 내장된 PSA Controller가 유효성을 검사한다. 따라서, 파드 내 컨테이너가 불필요한 권한을 가지지 않도록 PSA를 통해 PSS를 적용하여 운용해야 한다.
원인: container.securityContext.privileged == true
권장 설정:
PodSecurityAdmission 정책을 통해 컨테이너 권한을 제어한 경우
- allowPrivilegeEscalation=false
- runAsUser 설정
- runAsNonRoot=true
- capabilities.drop=ALL
- seccompProfile 적용
확인 명령어:
kubectl get pods --all-namespaces -o json | jq '.items[].spec.containers[].securityContext.privileged'
해결 방법:
privileged:false 설정 또는 보다 세분화된 권한으로 대체

CHK-M-ETCD-001: 암호화 활성화

위험도: 10/10
설명: etcd는 Kubernetes와 같은 분산시스템에서 중요한 데이터를 저장할 때 사용할 수 있는 키 값 분산 저장소 역할을 하고 있다. 따라서 etcd에 저장되는 데이터는 매우 민감하므로 공개되지 않도록 저장 시 암호화되어야 한다.
원인: --encryption-provider-config 플래그가 설정되지 않음 (etcd 데이터 암호화 미적용)
권장 설정:
etcd 암호화 방식이 aescbc 이상으로 설정된 경우
- --encryption-provider-config 설정
확인 명령어:
ps -ef | grep kube-apiserver | grep encryption-provider-config
# encryption-provider-config 내 설정된 경로의 암호화 설정 파일 분석을 통해 안전한 암호화 방식 사용 여부 확인
해결 방법:
kube-apiserver 매니페스트에 --encryption-provider-config 플래그를 추가하고 암호화 설정 파일 경로를 지정하세요. 암호화 방식은 aescbc 이상을 사용해야 합니다. 예: --encryption-provider-config=/etc/kubernetes/encryption-config.yaml

CHK-W-KUBELET-001: 인증 제어

위험도: 8/10

원인: Kubelet 인증 설정(clientCAFile)이 없음

- --client-ca-file 설정 (클라이언트 인증서 검증)
확인 명령어:
kubectl get nodes -o json | jq '.items[].status.nodeInfo.kubeletVersion'

각 노드의 /var/lib/kubelet/config.yaml에 clientCAFile 설정을 확인/추가하세요.

    clientCAFile: /etc/kubernetes/pki/ca.crt

설명: 파드의 컨테이너는 일반적으로 별도의 리눅스 네임스페이스에서 실행되므로 프로세스가 다른 컨테이너 또는 노드의 기본 네임스페이스에서 실행 중인 프로세스와 분리된다. 파드의 스펙에서 hostNetwork 옵션을 true로 설정하여 가상 네트워크 어댑터 대신 노드의 실제 네트워크 어댑터를 사용할 수 있으며 그 결과 해당 파드는 노드의 인터페이스를 사용하게 된다. 또한, hostNetwork 옵션과 유사한 파드 스펙 속성으로 hostPID와 hostIPC가 있다. 이를 true로 설정하면 파드의 컨테이너는 노드의 PID와 IPC 네임스페이스를 사용해 컨테이너에서 실행 중인 프로세스가 노드의 다른 프로세스를 보거나 IPC로 이들과 통신할 수 있다. 따라서, PSA(Pod Security Admission) 설정을 통해 호스트 IPC, PID, 네트워크 네임스페이스 사용을 방지하여 불필요한 권한을 제거해야 한다.
원인: 호스트 네임스페이스 공유 사용: hostPID=true
권장 설정:
네임스페이스 공유 금지 설정이 적용된 경우
- hostNetwork=false
- hostPID=false
- hostIPC=false
확인 명령어:
kubectl get pods --all-namespaces -o json | jq '.items[] | select(.spec.hostNetwork == true or .spec.hostPID == true or .spec.hostIPC == true)'
해결 방법:
파드 kube-bench-kwdd7의 spec에서 다음 설정을 false로 변경하세요:

- hostPID: false
- hostIPC: false
